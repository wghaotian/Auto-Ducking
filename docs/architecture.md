# Architecture proposal

## Metering finding and correction

The initial design assumed that querying `IAudioMeterInformation` from each enumerated session control would yield a process-isolated peak. That assumption is not part of Microsoft's documented contract. Microsoft documents `IAudioMeterInformation` as a meter for the stream to or from an audio endpoint.

On the target Windows 11 machine, a silent but continuously active Discord session returned a waveform correlated with Chrome playback. The values differed slightly because each COM call sampled the shared stream at a different instant, but the envelope was not isolated. `AudioSessionState` cannot filter this case because Discord deliberately keeps its output stream active while nobody is speaking.

The UI therefore uses the Audio Session API only for discovery, identity, volume, state, and PID metadata. Selected applications are measured with process loopback via `ActivateAudioInterfaceAsync`, `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, and `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`. Windows supplies only the target process tree's rendered PCM buffers. The utility computes an absolute peak and releases each buffer immediately; it never writes, retains, or decodes the content.

This identifies audio output from Discord rather than microphone input. It still cannot prove that the audio is speech: a Discord notification generated by the same process can produce a short peak.

## Identity and topology

The runtime model is:

```text
active render endpoint
  -> audio session (session-instance identifier)
       -> process metadata
       -> simple session volume

selected process IDs
  -> process-loopback capture (event driven)
       -> in-memory PCM absolute peak
       -> buffer released immediately
```

A PID is metadata, not identity. Browsers and other applications can expose several sessions, and PIDs can be reused. The prototype keys a session by endpoint ID plus `GetSessionInstanceIdentifier()`. It polls topology at a low rate and retains lightweight COM handles between refreshes for faster meter sampling. This handles new/expired sessions, application restarts, default-device changes, application routing, and Bluetooth endpoint reconnection without restarting the process.

For a later long-running service, polling can be supplemented with `IMMNotificationClient` (device changes) and `IAudioSessionNotification` (new sessions). A periodic reconciliation should remain as a safety net because notification registration and endpoint invalidation have race conditions.

## Runtime components

```text
CoreAudio topology + meters
          |
          v
Session classifier (VOICE / DUCK / IGNORE)
          |
          v
Peak activity detector per voice session
  activation threshold + dwell
  release threshold + dwell/delay
          |
          v
OR reduction across all VOICE sessions
          |
          v
Ducking state machine and smooth per-session ramps
          |
          v
ISimpleAudioVolume for DUCK sessions only
```

Configuration and logging sit outside these components so the monitor can later be hosted by either the current window or a tray application.

## Desktop UI boundary

The Win32 desktop UI is a thin host over the reusable Core Audio monitor, process-loopback meters, and activity detector. It selects one endpoint for discovery, starts an event-driven meter for each PID belonging to a checked executable, aggregates the maximum process peak by category, and renders two rolling histories. Application classification is stored by executable name so it survives session recreation and a process exposing several sessions.

The UI currently keeps settings and classifications in memory. Sliders and numeric editors share one bounded integer representation, preventing rounding drift. The release threshold is constrained to be no greater than the activation threshold. Device and session topology still refreshes independently of the display sampling timer.

This boundary is intentional: the UI does not own COM session handles. It passes detector state and selected application names to a reusable ducking controller, whose writer callback delegates keyed session updates to the Core Audio monitor. This keeps volume policy out of window-message handling.

## Activity detection

The aggregate selected voice peak is processed by a hysteresis state machine:

- transition inactive -> active only after peak remains above `activation_threshold` for `activation_ms`;
- transition active -> inactive only after peak remains below `release_threshold`, followed by `release_delay_ms`;
- the process meters are combined with a maximum reduction, so any selected communication application can activate ducking.

The thresholds and durations belong in configuration, not in the Core Audio layer. A notification beep can still activate the MVP if it lasts long enough. The detector interface should therefore accept a future envelope- or speech-specific implementation without changing the session monitor or ducker.

## Volume semantics and manual changes

`ISimpleAudioVolume` exposes an absolute session volume, not a separate attenuation layer owned by this utility. There is no native per-client multiplier that can be applied invisibly on top of the user's mixer setting. Consequently, manual changes require policy.

The implemented policy is cooperative rebasing:

1. On duck attack, capture each session's baseline and set `baseline * duck_factor`.
2. Tag the utility's own setter calls with a unique event-context GUID and remember the last value successfully written.
3. If a later topology snapshot differs from that value beyond a tolerance, interpret the observed ducked value as the user's new desired level and rebase the baseline to `observed / current_attenuation`.
4. On release, ramp to the rebased baseline.

This avoids fighting the user and preserves relative session volumes. The trade-off is that dragging the Windows slider while an attack/release ramp is moving can feel non-linear; ramp updates should pause briefly after an external change. All stored baselines must be bounded to 0.0-1.0.

## Failure safety

The ducking controller maintains an in-memory registry of every session it controls and its latest baseline. It restores synchronously when a target is unchecked, the output device changes, the update loop fails, or the UI closes normally. Restoration is best effort because a session can disappear before it is written.

No process can guarantee restoration after forcible termination, power loss, or an OS crash. A future version should persist a small recovery journal before the first volume change and clear it after successful restoration. On next launch it can attempt to match surviving session-instance IDs and offer recovery. Ducking via Windows' communications policy was considered but rejected because it is global policy, does not provide the requested application classification, and does not preserve control over which sessions trigger the duck.

## Performance

The UI displays at 20 Hz and reconciles topology at 1 Hz. Process-loopback capture is event driven and only runs for checked applications. PCM buffers cross the process boundary, but only a peak scalar survives each callback. Unchecked applications create no capture worker. Event notifications can later remove the need to poll topology.
